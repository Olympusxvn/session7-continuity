**Team position (do not keep claiming “15s indexer lag” as the bug):**

1. **`remember` is async.** Relayer returns `job_id` / `running`; vector is searchable only at `done`. Immediate recall sees the **old** fact because the **new** write has not landed. Documented fix: `remember` → `waitForRememberJob(job_id)` → `recall` ([quick start](https://docs.wal.app/walrus-memory/getting-started/quick-start)).
2. **`POST /api/forget` is synchronous.** Same-namespace recall after forget returns should not include deleted rows. “Stale” often = **wrong namespace** (forget `ca_voi_con::char::minh`, recall unified ns) or **duplicate append-only copies**.
3. **Dashboard Security Delete** *can* return a stale pointer: on-chain blob gone, relayer row cleaned **reactively** on next 404. They will track **eager cleanup**. Narrow path.
4. **They decline a client exclusion TTL cache** as the fix (would mask not-awaiting the write). Optional `exclude_ids` on recall is a separate convenience.

**Implication for us:** Continuity CLI already uses `rememberAndWait` (Day 1). Official MCP agents often `remember` then `recall` with no job wait — that gap belongs in **MCP/SDK harness**, not a 15s soft-filter story. Aligns with older [#409](https://github.com/MystenLabs/MemWal/issues/409) (job status visible to agents).
